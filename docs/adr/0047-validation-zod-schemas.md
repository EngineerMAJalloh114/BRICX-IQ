# 0047. `@bricx/validation`: bounded Zod schemas, generated reference data and a code-only error envelope

- Status: Accepted
- Date: 2026-10-14
- Deciders: Mohamed Abass Jalloh
- Source: P3-04 (plan approved 2026-10-14 16:09Z with rulings 1–8; architect scope items 1–6); the P3 standing rules (2026-10-13); STACK.md (Zod at every boundary); ADR 0023 (dependency policy); ADR 0045 (money) and ADR 0046 (i18n), whose patterns this ADR extends.

## Context

The ROADMAP P3-04 entry asks for Zod schemas for primitives (email, phone E.164, ISO country and currency, IANA zone, BCP 47, GeoPoint, `Money`), pagination and cursors, and a standard error envelope, with `z.infer` types exported. The architect added: `errors:money.<code>` keys in en, fr and ar for every `MoneyError` code with a drift test, validation as the only package with validation → money and validation → i18n edges; zod 4.6.5 only and `MoneySchema` reused, never redefined; a phone decision with evidence; bounds before parsing on every string, array and object with timing assertions; error output with codes, paths and i18n keys only.

Evidence (Node 24.22.0; npm registry and GitHub, 2026-10-14):

- libphonenumber-js: 1.13.15 was published 2026-10-08 (fails the 7-day rule); 1.13.14 2026-09-24T09:13:00Z, MIT, no dependencies, no install script. `/min` 123 KB minified (30 KB gzipped), `/max` 196 KB (51 KB gzipped). Metadata republished about every two weeks.
- datasets/country-list at commit `d214094` (2026-07-27, ODC-PDDL-1.0): 249 ISO 3166-1 alpha-2 codes, CSV SHA-256 `07f1554a…6293`.
- tzdb 2026e (eggert/tz commit `039ef27`, released 2026-09-29, public domain): 344 Zone names and 253 Link names in `africa`, `antarctica`, `asia`, `australasia`, `europe`, `northamerica`, `southamerica`, `etcetera` and `backward` (the plan said 340 zones; the extraction counts 344). No link in 2026e points at another link. `Africa/Freetown` is a link to `Africa/Abidjan`.
- Node 24.22.0's `Intl.DateTimeFormat` accepts all 344 canonical zones.

## Decision

### Phone (D1, ruling 1)

A hand-written strict E.164 check, no new dependency: `^\+[1-9][0-9]{6,14}$` (7 to 15 digits in total), at most 16 characters. No whitespace, punctuation, `00` prefix, extension or non-ASCII digit is accepted and nothing is trimmed: callers normalise. Output is unchanged, branded `PhoneE164`.

**This is a format check only.** It has no per-country length, no assignment check and no number-type check. Known false accepts, each with a test: an unassigned country code (`+999…`), too short or too long for its country (`+1202555`, `+232761234567890`), a national trunk prefix kept (`+44 0…`), an unallocated national range, the fictional 555 range, premium or shared-cost numbers. False rejects, each with a test: spaces, dashes, parentheses, dots, `00` prefix, national format, surrounding whitespace or newline, an extension, Arabic-Indic digits, a full-width plus, first digit 0. libphonenumber-js is deferred to P7 input formatting (a new ADR and DEPENDENCIES.md row then).

### Country (D2, ruling 2)

`data/countries.json` is generated by `scripts/gen-countries.mjs` from the committed CSV snapshot, pinned by commit and SHA-256 in `data/source/source.json`. A test requires the committed file to be byte-identical to a fresh run of the script. Uppercase alpha-2 only; `XK`, `EU` and user-assigned codes are rejected. `Intl.DisplayNames` was rejected: Hermes lacks it and it accepts non-ISO codes.

### Time zone (D3, ruling 3)

`data/time-zones.json` is generated by `scripts/gen-time-zones.mjs` from a committed snapshot of the Zone and Link lines of tzdb 2026e (`data/source/tzdb-2026e.tsv`), with the SHA-256 of the snapshot and of each upstream file. `--from-dir <checkout>` and `--source tzdb` re-extract from upstream and must report 0 differences. Zone and Link names are both accepted; **the output is always the canonical zone**, so a device's name is stored one way.

- (a) Links resolve transitively. The resolver throws on a cycle, a dangling target, a duplicate name or a link named like a zone. 2026e has no two-hop link, so the transitive case is proved with a fixture (`test/fixtures/tz/two-hop.tsv`, a three-hop chain), plus fixtures for each error.
- (b) A test checks that Node 24's `Intl.DateTimeFormat` accepts every canonical zone, with exceptions listed explicitly in the test (none at this commit). A tzdb release ahead of ICU shows up as a failing or listed exception, not silently.
- (c) **Canonicalisation changes the stored string**: `UTC` → `Etc/UTC`, `Asia/Calcutta` → `Asia/Kolkata`, and `Africa/Freetown` → `Africa/Abidjan` (tzdb merged Freetown into Abidjan; same rules since 1970). Sierra Leone users will see `Africa/Abidjan` stored; display names are a client concern (for architect review).

`Intl.supportedValuesOf` was rejected: its answer depends on each device's ICU version.

### Language tag (D4, ruling 4)

`LanguageTagSchema` reuses `@bricx/i18n`'s `normalizeLocale` (well-formed BCP 47, canonical form, 35 characters). Every `I18nError` it throws is caught and becomes `validation:invalid_language_tag`; no i18n error text reaches an issue or the envelope. `SupportedLocaleSchema` accepts `en`, `fr` or `ar` after canonicalisation (`invalid_locale` otherwise).

### Email (D5, ruling 5)

zod's default email pattern (`z.regexes.email`: ASCII, no quoted local parts, no IP literals), at most 254 characters, local part at most 64. No trimming; any whitespace is rejected. The output is **lowercased in full**, to match Keycloak's username and email handling; this is not an RFC guarantee (RFC 5321 local parts are case-sensitive).

### Currency and Money (D6)

`CurrencySchema` wraps `@bricx/money`'s `isCurrencyCode`/`parseCurrencyCode`; its issues carry money's own codes. `./money` re-exports the **same** `MoneySchema` and `MoneyJsonSchema` objects (a test checks identity); nothing is redefined.

### GeoPoint (D7)

A strict `{ lat, lng }` object: finite numbers, lat −90..90, lng −180..180, `-0` → `0`, an extra key → `unknown_field`. PostGIS stores (lng, lat); the mapping is explicit at the DB layer.

### Pagination (D8, ruling 8)

Opaque base64url cursor, at most 512 characters; the API (P4) owns its content. Page size an integer 1..100, default 25, given as a number or a strict digit string (`"25"`; `" 5"`, `"025"`, `"+5"`, `"1e1"`, `"5.0"` and `"0x10"` are rejected, each with a test); no `z.coerce`. `pageOf(item)` is `{ items (≤ 100), nextCursor | null }`.

### Error envelope (D9, D10, ruling 6, item 5)

RFC 9457-compatible body `{ status, code, key, traceId?, issues?: [{ path, code, key }], truncated? }`, with no `title` or `detail`. `code` is one of eight `ERROR_CODES`, each with a fixed status and the key `errors:<code>`. Issue codes are the 15 `VALIDATION_CODES` (key `validation:<code>`) or `money.<code>` for every `MoneyError` code (key `errors:money.<code>`). Schema issue messages are those keys or bare money codes; any other text (zod's English messages included) maps to `invalid_value` and is dropped.

- **Path segments are schema-declared property names or array indices only.** The envelope walks the schema (optional, nullable, default, prefault, readonly, catch, nonoptional, lazy, pipe, intersection and union unwrapped; budget 256 per level); any other segment, a record key above all, becomes `"*"`. A test parses a record whose attacker-chosen key holds a secret and requires the secret to appear nowhere in the envelope JSON.
- At most 100 issues (`truncated: true` beyond), 32 segments per path, 128 characters per segment.
- `parseAtBoundary(schema, input)` parses with a per-parse error map, so issues a caller's plain zod schema leaves to zod also become codes. `ErrorEnvelopeSchema` is what the client re-parses: bounded, strict, status and key must match the code.

### MoneyError keys (D11, item 1, ruling 7)

- `@bricx/money/errors` gains one export, `MONEY_ERROR_CODES` (frozen, in union order). **This is an addition to money after its 🔒 review (ADR 0045)**; nothing else in money changes. A compile-time assertion (`MoneyErrorCodesAgree`) requires the array and the `MoneyErrorCode` union to agree in both directions; `packages/money/test/codes-sabotage.test.ts` compiles copies of `errors.ts` where only the union (with its message) or only the array gains `fake_code`, and both must fail.
- `errors:money.<code>` for all 19 codes in en, fr and ar (57 strings). `MONEY_ERROR_KEYS` is a `Record<MoneyErrorCode, MessageKey>`: a new money code without a key fails `tsc` in `packages/validation` (a compiler sabotage proves it).
- Drift test (`packages/validation/test/codes.test.ts`): walks `MONEY_ERROR_CODES` and requires every key in en, fr and ar, argument-free, with fr and ar not copies of en (`i18n:check` already rejects empty messages). It never marks anything reviewed and never skips fr or ar: **the fr and ar text stays machine-drafted** (ADR 0046) until native review.
- Every key must match the i18n key pattern; `@bricx/i18n/limits` now exports `KEY_PATTERN` (the regex `i18n:check` already used) so the test uses the same one. If a money code ever fails it, the test names the code and fails; the fix is to rename the code in money (a reviewed change), never to transform or skip it here.

### Branded outputs (D12)

`Email`, `PhoneE164`, `CountryCode`, `TimeZone`, `LanguageTag`, `Cursor` and `TraceId` are branded; `z.input`/`z.output` types are exported. Type tests prove a raw string is not assignable to a branded type; compiler sabotage removes the `Email` and `PhoneE164` brands and the `@ts-expect-error` lines go unused.

### Bounds (D13, item 4, ruling 8)

Every string's length is checked before its format check runs (`continue: false`); every object's own enumerable keys are counted (stopping past 16) before zod reads a field; every array's length is checked before an element is parsed. Tests prove the work is not done: the format `check` functions are spied on and never called for oversized input, objects with counting getters and arrays behind counting proxies are never read. A generous ratio backstop (1 MB input under 50 times a 1 KB input) replaces millisecond limits, which would flake on the slower CI runner.

### Coverage, boundaries, lint (D14, D15, D16)

- `packages/validation` joins `STRICT_PATHS` (95% lines), with a `strict-validation-below` vitest smoke case.
- Boundaries element `validation` (`packages/validation/src/**`, anchored): its source may import `@bricx/ids`, `@bricx/money`, `@bricx/i18n`, its own `data/` and `zod`, nothing else (no other workspace package, npm module or Node built-in). ids, money, i18n and domain may not import it; money and i18n may not import each other. Smoke fixtures for each edge and `check-real.mjs` probes at the real paths. The clock and `Math.random` bans extend to `packages/validation/src`.
- Semgrep: no rule change; the CI scan covers the package.

### Dependencies

`zod` 4.6.5 (already allowed, ADR 0039) and `fast-check` 4.10.2 (dev, already allowed, ADR 0045). No new package; the lockfile gains only the importer block.

## Deviations from the plan (for architect review)

- An extra export `./limits` (the `LIMITS` table), so callers can show the caps.
- `@bricx/i18n/limits` exports `KEY_PATTERN` (previously private in `check.ts`), so the drift test uses the checker's own regex.
- The page-size code is `invalid_page_size`, not `invalid_limit` as named in the plan; the envelope builder is `validationEnvelope`/`parseAtBoundary`, not `toErrorEnvelope`.
- Three test files were corrected for type errors after the red run (`codes.test.ts`, `data.test.ts`, `error-envelope.test.ts`); no assertion was weakened; the made-up secret in `error-envelope.test.ts` and `checks.ts` was changed from a Stripe-shaped string, which gitleaks flagged, to `attacker-secret-DO-NOT-LEAK-7f3a9c41`, with the same assertions.

## Consequences

- Positive: one bounded, branded schema per primitive used by API, worker and devices; reference data reproducible from pinned public-domain sources; error output that can never echo input or library text; a money code without a translation fails the build.
- Negative (for architect review): phone checks format only until P7; canonical zones change what a device reported (`UTC` → `Etc/UTC`, `Africa/Freetown` → `Africa/Abidjan`); tzdb and country data need a manual refresh; 60 machine-drafted fr and ar strings (38 money, 22 validation) await native review; email lowercasing differs from RFC 5321.

## Follow-ups

- **P7:** libphonenumber-js for input formatting and per-country checks (ADR + DEPENDENCIES.md row then); confirm `Intl.getCanonicalLocales` on Hermes for `LanguageTagSchema` ("Hermes: must confirm at P7").
- **Each tzdb release:** update the pinned commit and hashes, regenerate, and keep the Intl exception list explicit.
- **Before production:** native review of the fr and ar `errors:money.*` and new `validation:*` text.
