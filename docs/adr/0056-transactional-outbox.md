# 0056. Transactional outbox: `bricx.outbox`, `insertOutbox()`, the `bricx_relay` role and the worker's relay

- Status: Accepted
- Date: 2026-10-16
- Deciders: Mohamed Abass Jalloh
- Source: P4-06 (task plan approved 2026-10-16 14:05Z: decisions 1–11 as ★ and conditions 1–7, plus three CHECK constraints); CLAUDE.md rules 3, 4, 5, 6, 7 and 12; ADR 0023 (dependency policy), ADR 0035 (database roles), ADR 0043 (Semgrep), ADR 0052 (migrations), ADR 0053 (`withTx()`), ADR 0054 (RLS framework).

## Context

CLAUDE.md rule 5: side effects (jobs, notifications, payments, webhooks out) go through the outbox in the same transaction; a request never enqueues BullMQ directly. ROADMAP P4-06 asks for an `outbox` table, an `OutboxService.enqueue(tx, topic, payload)`, and a relay in `apps/worker` that publishes committed rows to BullMQ with jobId = the outbox id, so a rolled-back transaction produces no job and a committed one exactly one, even across a relay crash.

The relay must read every org's rows. Every other access to the database is `withTx()` with a tenant context (rule 4, ADR 0053), and `bricx.outbox` is FORCE RLS like every table. The relay therefore needs its own role and its own transaction helper, and both have to stay as narrow as possible.

## Decision

### The table (migration `0002_outbox`, decision 1)

`bricx.outbox`: `id uuid` (UUIDv7, generated by the API, rule 6), `org_id uuid`, `topic text`, `payload jsonb`, `created_at`, `published_at`, `attempts integer`, `next_attempt_at`, `last_error text` (a code, never a message), `dead_at`; all times `timestamptz` from the database's `now()`.

- CHECKs: `topic ~ '^[a-z][a-z0-9_.]{0,62}$'`, `attempts >= 0`, `NOT (published_at IS NOT NULL AND dead_at IS NOT NULL)`, `last_error ~ '^[a-z][a-z0-9_]{0,63}$'`.
- Partial index `outbox_pending (created_at, id) WHERE published_at IS NULL AND dead_at IS NULL`.

### Row-level security (decision 2, condition 7)

`enableOutboxRls()` in `@bricx/db/rls` emits the policies, appended to the migration; the table is registered in `SYSTEM_TENANT_TABLES`, and the RLS integration test proves them.

- ENABLE + FORCE.
- `bricx_app`: `INSERT` only, on `(id, org_id, topic, payload)`, `WITH CHECK (org_id = app.current_org())`. No SELECT, so no `RETURNING` and no `ON CONFLICT` (both need SELECT): `insertOutbox()` uses an app-side id and returns nothing, and its tests run as `bricx_app`.
- `bricx_readonly`: nothing.
- `bricx_relay`: `SELECT`, and `UPDATE` on the delivery columns (`published_at, attempts, next_attempt_at, last_error, dead_at`) only, through policies `TO bricx_relay USING (true)`. No INSERT, no DELETE, no other table.
- `bricx_owner` has no outbox policy: under FORCE it sees and changes no row. Retention (P13) is a partition drop or an explicit owner DELETE policy, decided then.

### The `bricx_relay` role (decision 3, condition 6; amends ADR 0035)

The dev bootstrap creates `bricx_relay` `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, `search_path = bricx, pg_temp`, `idle_in_transaction_session_timeout = '20s'`, CONNECT on the database and USAGE on `bricx` only. Its password is `BRICX_RELAY_PASSWORD`; the worker connects with `RELAY_DATABASE_URL`, a `Secret` in `@bricx/config/worker` that the API's key list never holds. An existing dev volume is detected by `dev:up` and needs `pnpm dev:reset`. P13 creates the role in the RDS bootstrap.

### `withRelayTx()`: a documented exception to rule 4 (decision 4, condition 7; amends ADR 0053)

`openRelayDatabase(url).withRelayTx(fn)` in `@bricx/db/database` is the one database path that is not `withTx()`. It sets no tenant context. It is safe only because:

- it asserts `current_user = 'bricx_relay'` first (`RelayRoleError`, `fn` never runs), so a wrong URL cannot run cross-org statements as another role;
- it sets a transaction-local `statement_timeout` of 30 s, and the role's `idle_in_transaction_session_timeout` ends a transaction a stuck relay leaves open;
- it cannot nest in itself or in `withTx()`;
- `bricx_relay` can reach nothing but the outbox columns above;
- Semgrep `bricx-relay-tx-outside-relay` allows `openRelayDatabase` and `withRelayTx` only in `packages/db/`, `apps/worker/src/relay/` and `apps/worker/test/` (for architect review).

CLAUDE.md is not edited here; the owner raises the wording of rule 4 separately.

A lost connection inside `withRelayTx()` (a terminated backend, a cut network) is caught by an `error` listener on every pool client, so the transaction rejects and the worker does not crash.

### Writing to the outbox (decision 5, condition 5)

- `insertOutbox(tx, topic, payload, id)` in `@bricx/db/outbox` validates before any SQL: the topic is registered, the id is a canonical UUIDv7, and the payload is a plain object whose top-level keys the topic registers, holding only plain objects, dense arrays, safe integers, booleans, null and well-formed strings without NUL, at most 32 deep and the topic's `maxBytes` (at most 64 KiB) of UTF-8 JSON, checked iteratively before serialising. The org is the transaction's (`app.current_org()`), never the caller's. Every refusal is an `OutboxError` with a code and no input value.
- Payloads carry ids, not personal data: a consumer reads what it needs in its own transaction.
- The topic registry `OUTBOX_TOPICS` is frozen and holds `system.ping` (payload `{}`, queue `system`), which proves the pipeline. A topic is added with its consumer.
- `OutboxService.enqueue(tx, topic, payload)` in `apps/api/src/modules/outbox` (exported through `public-api.ts`) is a thin Nest wrapper: it generates the id with the injected `Clock` and calls `insertOutbox()` in the caller's transaction.
- `apps/api` and `apps/worker` do not depend on each other in either direction; both use `@bricx/db`.

### The relay (decisions 6 and 7, conditions 1, 3 and 6)

`apps/worker/src/relay`. One batch is one `withRelayTx()`:

1. claim up to 100 pending, due rows, oldest first, `FOR UPDATE SKIP LOCKED` (two relays never hold the same row);
2. for each row, validate topic and payload again, then `Queue#add(topic, data, { jobId: outbox id })` on the topic's queue, bounded by 5 s;
3. mark the published rows `published_at = now()` and the failed rows failed, in the same transaction, then COMMIT.

A crash between an add and the COMMIT leaves the row pending; the next add has the same jobId, and BullMQ returns the existing job. Completed and failed jobs are kept 24 h (`removeOnComplete/removeOnFail: { age: 86400 }`), the dedupe window. Delivery is at least once; consumers stay idempotent.

Failures:

- **Infrastructure** (condition 1): Valkey unreachable, timing out (ioredis' 5 s command timeout and the relay's own bound), out of memory, loading or read-only; or any other add error while Valkey does not answer PING; or Postgres failing. The batch stops, the rows not yet published stay untouched (attempts unchanged, never dead-lettered), what was already published commits, and the relay backs off globally: 1 s doubling to 30 s. `outbox.relay_unavailable` (warn, `dependency: valkey | database`) is logged when an outage starts and then at most once a minute; `outbox.relay_recovered` once when it ends. A BullMQ `Queue` first used during an outage keeps its failed initialisation, so the publisher drops it on an infrastructure failure and the next add starts a fresh one.
- **Row** (unknown topic, invalid payload, an add Valkey rejects while answering PING): `attempts + 1`, `last_error` = the code, next attempt after min(2^attempts s, 300 s); dead (`dead_at = now()`) at `OUTBOX_DEAD_LETTER_AFTER` (default 10, 1–100), logged as `outbox.dead_letter` (error) with ids, topic, attempts and code, only after the COMMIT.
- **Batch deadline** (condition 6): past 15 s, the relay commits what it published and stops the batch; the next batch starts at once.

The loop polls every 1 s when idle and runs again at once after a full batch or a deadline. Re-driving a dead letter is one `UPDATE` as `bricx_relay`, in `docs/runbooks/outbox.md`; an integration test runs that exact block as `bricx_relay` (1 row, then 0) and as `bricx_owner` (0 rows).

### Valkey must not evict (condition 4)

Compose Valkey runs with `--maxmemory-policy noeviction`. The worker reads `CONFIG GET maxmemory-policy` at boot and refuses to start otherwise (`worker.boot_failed`, code `valkey_eviction_policy`): an evicting Valkey can drop a job whose row is already marked published. Managed Valkey may block `CONFIG`; P13 decides between allowing it and reading `INFO memory` (for architect review). P13 also sets production persistence and `noeviction`.

### The worker process (decision 11)

`apps/worker` is a plain Node process (no Nest), started by `pnpm dev:worker` (no compose service yet). `main.ts` validates config first and loads nothing else before it; a bad environment exits 1 naming keys only. Boot checks Valkey (`valkey_unavailable`, `valkey_eviction_policy`) and the relay database (`database_unavailable`, `relay_role`), then starts the relay and logs `worker.started`. SIGTERM or SIGINT stops it after the batch in flight, closes queues and connections, logs `worker.stopped` and exits 0. Logs are pino JSON, written synchronously, with ids, topics and codes only.

### Semgrep (decision 10)

Two rules written for this repository, with self-test fixtures:

- `bricx-bullmq-outside-worker`: any import, re-export, `require` or dynamic import of `bullmq` outside `apps/worker/`.
- `bricx-relay-tx-outside-relay`: as above.

`bricx-bullmq-outside-outbox` (ADR 0043) still limits `Queue#add` to `apps/worker/src/relay/`.

## Consequences

- A request that needs a side effect calls `OutboxService.enqueue(tx, …)` inside its `withTx()`; it commits or rolls back with the change.
- Each new topic needs a registry entry, a consumer and a payload of ids.
- After merging, a developer runs `pnpm dev:reset` (new role, new Valkey flag), then `pnpm db:migrate`.
- P13 "Also" lines: `bricx_relay` in the RDS bootstrap; outbox retention; production Valkey persistence and `noeviction`; alerting on `outbox.dead_letter` and `outbox.relay_unavailable`.

## Alternatives rejected

- Running the relay as `bricx_owner` or with BYPASSRLS: far wider than SELECT and five columns of one table.
- A per-org relay loop through `withTx()`: needs the list of orgs (another cross-org read) and one transaction per org per poll.
- `LISTEN/NOTIFY` instead of polling: still needs the poll for missed notifications; can come later without changing the table.
- Counting every failed add as an attempt: a Valkey outage would dead-letter healthy rows (condition 1).
- `@nestjs/bullmq` in the API: the API never produces jobs directly (rule 5).
