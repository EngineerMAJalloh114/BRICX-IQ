## Context

ROADMAP P4-02 asks for the shared column helpers, tables in schema `bricx` (`schemaFilter: ['bricx']`), migrations generated by drizzle-kit and hand-reviewed, `pnpm db:migrate` running as `bricx_owner`, a migration guard that rejects `CREATE PUBLICATION` and `DROP PUBLICATION`, the `bricx_owner` URL as a new `@bricx/config` key, and `docs/runbooks/migrations.md` (forward-only, expand/contract).

Evidence (Node 24.22.0; raw output in the PR and the proofs folder):

- `bricx_owner` has `CONNECT` on the database and nothing else there (ADR 0035): it owns schema `bricx` but may not create a schema. In Postgres 18, `CREATE SCHEMA IF NOT EXISTS` checks the database `CREATE` privilege before it checks existence, so it fails with "permission denied for database" even when the schema exists (shown in a scratch container during planning).
- drizzle-orm 0.45.4's Postgres migrator always runs `CREATE SCHEMA IF NOT EXISTS` for its migrations schema (`pg-core/dialect.js:54`), so it cannot run as `bricx_owner` without widening that role.
- drizzle-kit 0.31.11 emits `CREATE SCHEMA "bricx";` in a migration whenever a `pgSchema()` object is **exported** from the schema entry it reads (`prepareFromExports`, `bin.cjs:16727`). Tables declared through a schema object that is not exported produce no `CREATE SCHEMA` (tried both ways).
- drizzle-kit exits 0 even when it fails to write (seen with an absolute `out` path: ENOENT, exit 0). Callers must check the files, not the exit code.

## Decision

### Schema (D3(a))

- `01-bootstrap.sh` creates `bricx_migrations AUTHORIZATION bricx_owner` and revokes everything from `PUBLIC`: no grant and no default privilege for any role, and outside `bricx`, so the RLS and default-privilege rules of `bricx` never touch it. The history table `bricx_migrations.applied (idx integer PRIMARY KEY, tag text UNIQUE, sha256 text, applied_at timestamptz)` is created by the migrator on first run, owned by `bricx_owner`.
- `pnpm dev:up` checks the new schema with the other bootstrap objects (`bootstrapObjects` in `scripts/guards.mjs`), so an existing dev volume stops with a `pnpm dev:reset` instruction. Its message now says "created by an older bootstrap script".
- The production RDS bootstrap must create the same schema (ROADMAP P13-01 and P13-03 "Also" lines).

### Config (D4)

- `@bricx/config/migrate`: `loadMigrateConfig()` reads exactly `NODE_ENV` and `MIGRATION_DATABASE_URL` (a `Secret`). Production rejects a `dev-only` value and a local host (`MIGRATION_DATABASE_URL` joins `remoteOnlyKeys`). The api and worker key lists never include it (tested).
- `.env.example` gains `MIGRATION_DATABASE_URL` for `bricx_owner`, tested to match `BRICX_OWNER_PASSWORD` and `POSTGRES_DATABASE`. `pnpm dev:up` already appends a key `.env` lacks without overwriting any value and prints only key names (`completeEnv` in `scripts/dev-stack.mjs`); two `envMerge` fixtures now cover this key (missing: appended; present with another value: kept).

### Migrator (D14(a))

`migrate(url, folder?)` in `@bricx/db/migrate` applies drizzle-kit's output itself:

- Reads `meta/_journal.json` (dialect `postgresql`, `breakpoints: true`, tags `NNNN_name`, `idx` strictly increasing; gaps allowed so a gap fill is detectable) and each `<tag>.sql`, split on `--> statement-breakpoint`. Refuses an unlisted `.sql`, a missing file, a journal over 1 MiB or a file over 8 MiB (bounds checked before reading; for architect review), all before connecting.
- Asserts `current_user = 'bricx_owner'` first (`wrong_role`, change 3), then that `bricx_migrations` exists and is owned by `bricx_owner` (`missing_schema`).
- Takes a session advisory lock (`pg_advisory_lock(hashtext('bricx_migrations'))`): a concurrent run waits, then finds nothing to do.
- Before running anything, refuses: an applied tag no longer in the journal (`applied_migration_removed`), an applied tag at another `idx` (`applied_migration_reordered`), an applied file whose SHA-256 changed (`applied_migration_changed`), and a pending migration whose `idx` is below the highest applied one (`gap_fill`, change 2).
- One transaction per migration: its statements and its history row commit together. A failure rolls back and throws `migration_failed` with the tag, the 1-based statement index, the SQLSTATE and the server's message (not its detail, not the statement text; for architect review). A connection failure is `database_unavailable` with no message detail and no cause.
- `MigrationError` carries a code and at most a tag; the URL is revealed only to the driver.

The CLI is `apps/api/src/migrate.ts`, built with the api and run through P4-01's resolve hook: it calls `loadMigrateConfig()` first, imports the migrator after, prints `db:migrate: applied N (tags)` or `db:migrate: 0 applied`, and exits 1 on a `ConfigError` or `MigrationError` (message only). Root scripts:

- `db:migrate`: `pnpm --filter @bricx/api build && node --env-file=.env --import ./apps/api/dist/register.js apps/api/dist/migrate.js`. The env flag lives in the root script because packages may never load env files and the api's only env-file script is `dev` (both tested); `@bricx/api`'s own `migrate` script has no env file (a deploy job supplies the environment).
- `db:generate`: `pnpm --filter @bricx/db generate` (`drizzle-kit generate`, offline, no URL).

### Schema helpers

- `pgSchema("bricx")` lives in `src/schema/namespace.ts` and is **not** exported from `src/schema/tables.ts`, drizzle-kit's entry, so no migration ever creates the schema (tested: the entry exports no `PgSchema`). `@bricx/db/schema` re-exports it for application code.
- Column helpers in `src/schema/columns.ts`, each a fresh builder: `id()` uuid primary key, default `uuidv7()` (Postgres 18 built-in; syncable ids still come from the device, rule 6); `orgId()` and `createdBy()` uuid not null; `createdAt()` and `updatedAt()` timestamptz not null default `now()`; `version()` integer not null default 1; `deletedAt()` nullable timestamptz. Timestamps use `mode: "string"` (ISO strings, not `Date`; for architect review).
- `drizzle.config.ts`: schema `./src/schema/tables.ts`, out `./migrations`, `schemaFilter: ["bricx"]`, `strict`, `verbose`. The journal starts empty (D15); P4-03 onwards add tables.

### Guards

- `check:workspace` (`migrationSqlProblems`, proven by 10 fixtures): no migration may `CREATE PUBLICATION`, `DROP PUBLICATION`, or `ALTER PUBLICATION … RENAME` / `OWNER TO`, in any case, across lines and after comments (comments are stripped first, so a commented-out statement passes). `ALTER PUBLICATION powersync ADD TABLE` is how a migration publishes a table. Every `.sql` is in the journal and every journal entry has its file.
- `scripts/migrations-immutable.mjs` (change 4; the CI step is for architect review): on a `pull_request` event, diffs `packages/db/migrations` from the merge base with `origin/$GITHUB_BASE_REF` to `HEAD` and fails on an edit, delete or rename of a merged `NNNN_*.sql` and on any `_journal.json` change other than appended entries. On any other event it says so and passes, because workflows may not use `if:` (ADR 0031). The rules are `migrationImmutabilityProblems` in `guards.mjs` (11 fixtures); `--selftest` proves the git plumbing in a throwaway repository (5 cases). The CI `security` job (full history) runs the self-test, then the check; `check:workspace` fails if either step or `fetch-depth: 0` goes missing (5 fixtures).

### Tests (D8, D16)

The migrator's integration tests run in CI's existing `integration` job against compose.yml's Postgres with the real init folder: an empty database, then each prefix in order, give the same catalog snapshot (relations with owner and ACL, columns, constraints, indexes); the real journal runs from empty and through each prefix; one fixture set is produced by running `drizzle-kit generate` inside the test (change 1). The previous-release-snapshot step moves to P13-03 (no release exists yet).

## Consequences

- Migrations run only as `bricx_owner`; the history is invisible to every other role.
- A merged migration is never edited: a fix is a new migration (runbook).
- The first migration that adds a table must not export a `pgSchema()` from `tables.ts`; the unit test fails if it does.
- `db:migrate` builds the api first, as `dev:api` does.

## Negatives (for architect review)

- Our migrator is code we own instead of drizzle-orm's. It is small and covered by integration tests; drizzle-orm stays for the schema builders and, from P4-03, queries.
- Gaps in `idx` are allowed by the reader (needed to detect a gap fill); drizzle-kit never writes them.
- `migration_failed` includes the server's message, which can name objects from the migration (never values from application data: migrations hold DDL).
- `@esbuild-kit/*` are deprecated upstream; they arrive only through drizzle-kit, dev-only.

## Alternatives rejected

- drizzle-orm's migrator with `CREATE` on the database granted to `bricx_owner` (widens the owner role) or with the history table in `bricx` (the migrator would still run `CREATE SCHEMA IF NOT EXISTS`).
- Stripping `CREATE SCHEMA` from generated SQL by hand on every first migration (the namespace split prevents it at the source).
